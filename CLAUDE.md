@AGENTS.md

## Commands

Package manager is pnpm (pinned via `packageManager`).

```bash
pnpm dev                              # dev server (Turbopack) on http://localhost:3000
pnpm build                            # production build (also type-checks)
pnpm lint                             # ESLint (flat config, eslint-config-next core-web-vitals + typescript)
pnpm lint path/to/file.tsx            # lint a single file
pnpm exec tsc --noEmit                # type-check only
pnpm dlx shadcn@latest add <name>     # add a shadcn/ui component into components/ui/
pnpm db:indexes                       # create the MongoDB indexes (ensureIndexes, scripts/ensure-indexes.ts); safe to re-run
pnpm db:migrate-payments              # rewrite payments from the old one-unit shape (scripts/migrate-payment-units.ts); safe to re-run
pnpm seed:units                       # add the condo's units (scripts/seed-units.ts, run with tsx); skips existing ones
```

There is no test runner configured.

## Commits

Always commit with short messages: a single concise subject line (e.g. `Add login page`), no body.

## Stack

Next.js 16.4 (App Router) · React 19.3 · TypeScript strict · Tailwind CSS v4 · shadcn/ui on Base UI · pnpm.

The Next.js version is newer than most training data — per `AGENTS.md`, read the relevant guide under `node_modules/next/dist/docs/` before writing Next-specific code. Things already in use here that differ from older Next:

- `next.config.ts` enables `cacheComponents` and `partialPrefetching`. With Cache Components on, uncached/request-time data access in a Server Component has to sit behind `<Suspense>` or be explicitly cached — check the docs before adding data fetching.
- Session checks wait for the request: `lib/supabase/server.ts` calls `await io()` before creating the client, because Supabase compares the session's expiry with the current time and Next otherwise reports `Date.now()` during prerendering. Anything that awaits it (directly or through `getCurrentUser()`) must therefore sit inside a `<Suspense>` placed in or below the layout shared with the previous page, or Next reports a blocking navigation. That is why `app/(app)/layout.tsx` and `app/(app)/(admin)/layout.tsx` are plain layouts wrapping an inner async component in `<Suspense>`, and why the login, forgot-password and set-password pages render `RedirectIfSignedIn` / `RedirectIfSignedOut` (`components/auth/SessionRedirect.tsx`) inside `<Suspense>` instead of awaiting the session themselves.
- Layout/page props use the globally generated `LayoutProps<"/route">` / `PageProps<"/route">` helpers (see `app/layout.tsx`) rather than hand-written prop types.
- Tailwind is wired through a Turbopack loader rule (`@tailwindcss/turbopack` in `next.config.ts`), not PostCSS. There is no `postcss.config.*` and no `tailwind.config.*`; all theme configuration lives in `app/globals.css`.

## Architecture

The product is an app for **Hacienda del Carmen Playa** (the name shown on the login screen). `SPECS.md` is the product spec and data model; its minimal version (section 6) is built except supporting files (6.6), which need the S3 bucket.

- `app/login/page.tsx` — two-column login screen rendering `components/login-form.tsx`, which composes the OAuth buttons in `components/auth/`.
- `app/(app)/layout.tsx` — the shell for every signed-in page: checks the session with `getCurrentUser()` (redirects to `/login`), sends a Supabase user with no document or a deactivated one to `/auth/no-access` (a client page that signs them out), then renders `SidebarProvider` → `AppSidebar` (menu filtered by `getRole(profile)`) + `SidebarInset` with `SiteHeader` and `{children}` as the right panel. New signed-in pages go inside `(app)` and render only their own content. `SiteHeader` takes its title from the menu item matching the current path. `LocaleSync` applies the language saved on the account when the browser shows another.
- `app/(app)/page.tsx` (`/`) — the dashboard, the same for every role: the user's own units first (`UnitBalanceCards`), the current month's income, expenses, result and account balances (`getLedgerMonth()`), and the units with overdue amounts.
- Pages every signed-in user can open, outside `(admin)`: `accounts/` (balances; the admin also adds and edits accounts), `transactions/` (the ledger for one month, `?month=YYYY-MM`; the admin adds income, expenses and transfers, edits and cancels them with a reason, all subject to the month lock; transactions created by payments are corrected from Payments), `unit-balances/` (transparency rule: what every unit owes and has overdue), `my-units/` (the units the user owns) and `units/[unitId]/` (one unit's balance, charges, payments, tenants and licence plates; only its current owners and the admin get in, through `getAccessibleUnit()`, and they edit tenants and plates there). `history/` shows the audit trail to the committee and the admin. Their queries are in `lib/data/ledger.ts`, `lib/data/unit-accounts.ts` and `lib/data/history.ts`; each returns a `canManage` flag or null rather than throwing for a role that may only look.
- `app/(app)/(admin)/layout.tsx` — admin-only pages; redirects non-admins to `/`. Route groups don't appear in URLs, so `app/(app)/(admin)/users/page.tsx` is `/users`.
- `app/(app)/(admin)/users/` — the users list, and the pattern for data pages: `page.tsx` renders the frame and wraps an async Server Component (`users-table.tsx`) in `<Suspense>` with a skeleton fallback; the query lives in `lib/data/` (`getUsers()`), re-checks the role itself with `requireAdmin()` from `lib/auth.ts`, and returns plain objects (no `ObjectId`/`Date`) so rows can reach Client Components. Statistics cards (`users-stats.tsx`, `getUserStats()`) stream in their own `<Suspense>` above the table. `user-form-dialog.tsx` is the create/edit modal (no `user` prop = create), opened by `add-user-button.tsx` and by the Edit row action; creating calls the `createUser` Server Action in `actions.ts` (admin check, `userInputSchema`, Supabase `inviteUserByEmail` through `lib/supabase/admin.ts` with `SUPABASE_SECRET_KEY`, then the MongoDB insert with status `invited`, undoing the Supabase user if the insert fails, then `refresh()`); editing calls `updateUser` (everything but the e-mail), and the row menu deactivates or reactivates an account with `setUserActive` (status in MongoDB, plus a Supabase ban so no session can be opened). An admin cannot remove their own role or access.
- `app/(app)/(admin)/units/` (`/units`) — the units list, built like the users page: statistics (`units-stats.tsx`, `getUnitStats()`; the ownership-share card warns when shares do not add up to 10,000), an Add button, then the table (`units-table.tsx`, `getUnits()` and `getOwnerOptions()` in `lib/data/units.ts`). `unit-form-dialog.tsx` creates or edits: identifier, ownership share out of 10,000 (`OWNERSHIP_SHARE_TOTAL`), current owners picked from users with the owner role (multi-select), the date an owner change takes effect, and the parking spaces' labels. `saveUnit` in `actions.ts` validates with `unitInputSchema` and keeps ownership history: an owner who is removed gets `to` set to that date, a new one is appended with `from`. A parking space keeps its plates through its id. The row menu also opens the unit's detail page.
- `app/(app)/(admin)/categories/` (`/categories`) — income and expense categories with a Spanish and an English name. The one with `system: "fees"` is used by payments: only its names can change.
- `app/(app)/(admin)/fees/` (`/fees`) — fees admin, one page with statistics and three sections, each an async Server Component in its own `<Suspense>` with its dialog as the section button: the maintenance fee settings (`fee-settings.tsx`, `saveFeeSetting`: a new `feeSettings` entry per change, refused for a month that already has fees or an earlier one), the monthly fees (`monthly-fees.tsx`, `generateFees`: one regular charge per unit for the chosen month, skipping units that already have it) and the special assessments (`special-assessments.tsx`, `createSpecialAssessment`: the assessment plus one charge per unit). Every unit is charged, and only when the ownership shares add up to `OWNERSHIP_SHARE_TOTAL`. The maths (`splitByShares` with largest remainders, `findFeeSetting`, calendar dates as midnight UTC) is in `lib/fees.ts`, which is client-safe because the dialogs preview each unit's amount with it; queries are in `lib/data/fees.ts`. Nothing can be cancelled or edited once generated.
- `app/(app)/(admin)/payments/` (`/payments`) — payments admin: statistics (received this month; what is owed and overdue, split in regular fees and special assessments), the list, and two actions in `actions.ts`. A payment can cover several units and months: it has one entry per unit in `units` (the unit's part, its `allocations` to charges and its `unallocatedAmount`) and an optional `reference` (the bank statement's folio). The dialog lists the chosen units' unpaid charges with an amount each, pre-filled by `distributePayment` (`lib/payments.ts`: oldest charge first across the units, the rest as credit split by ownership share) until the admin edits a line; choosing an owner selects their units. `recordPayment` checks every line against the charges (a unit keeps credit only when all its charges are covered), pays those charges and saves the payment with one income transaction for the whole amount (category: the built-in one with `system: "fees"`, created on first use). Credit stays in the unit's `unallocatedAmount`; `applyUnitCredit` (`lib/payment-allocation.ts`) applies it to the unit's unpaid charges oldest first, and the fees actions call `applyCredit()` after creating charges so a credit is used at once. `cancelPayment` needs a reason, marks the payment and its transaction cancelled and gives the amounts back to the charges of every unit. Both refuse a month that is locked (`isMonthLocked` in `lib/payments.ts`: more than 7 days after the month ends; "today" comes from `condoToday()` in `lib/condo-time.ts`). The writes go through `withTransaction` (`lib/mongodb.ts`), which is a real transaction on a replica set and plain sequential writes on a standalone server such as local development. Proof-of-payment files are not implemented.

Component layers:

- `components/ui/` — shadcn-generated primitives. Style is `base-vega` (`components.json`), meaning they wrap **`@base-ui/react`**, not Radix. Base UI's API differs from Radix (e.g. composition via the `render` prop instead of `asChild`, `data-*` state attributes like `data-vertical`), so don't paste Radix-flavoured shadcn snippets in unchanged.
- `components/*.tsx` — block-level compositions (sidebar, nav-*, login form) and the pieces pages share: `stats-cards.tsx`, `table-skeleton.tsx`, `row-actions.tsx` (the row "⋮" menu), `reason-dialog.tsx` (asks why before a cancellation), `balance-cards.tsx` and `unit-balance-cards.tsx`.
- The sidebar menu is data-driven: `config/menu.json` lists groups and items (`label`, `path`, `icon`, optional `roles` per group; `label` is a key in the `Menu` messages namespace, not display text), and `lib/menu.ts` maps icon names to `lucide-react` components and filters groups by role. To add an item, edit the JSON; a new icon also needs an entry in the `menuIcons` map.
- `components/auth/` — app-authored components; these use PascalCase filenames, unlike the kebab-case shadcn files.

Auth is Supabase via `@supabase/ssr`, with three clients in `lib/supabase/`: `client.ts` (browser), `server.ts` (Server Components / route handlers, cookie-backed) and `proxy.ts` (session refresh). The root `proxy.ts` runs `updateSession` on every non-asset request and redirects unauthenticated users to `/login` for everything except `/login` and `/auth/*`. Pages also check the session themselves with `getClaims()` via the server client: `app/(app)/layout.tsx` (through `getCurrentUser()`) redirects to `/login` when there is no user, and `app/login/page.tsx` redirects to `/` when there is one. Sign-in happens client-side: `components/login-form.tsx` calls `signInWithPassword` and the buttons in `components/auth/` call `signInWithOAuth` (Google, Facebook), which returns through `app/auth/callback/route.ts` to exchange the code for a session. Both paths land on `/`; a failed OAuth exchange goes to `/login?error=oauth`. Sign-out is the "Log out" item in `components/nav-user.tsx` (`signOut()` on the browser client, then `/login`). E-mailed links (invitation, later password reset) come back to `app/auth/confirm/page.tsx`, a Client Component: Supabase puts the tokens in the URL fragment (invitations cannot use PKCE), so it reads them in the browser, calls `setSession` and goes to `/auth/set-password`; a bad or expired link goes to `/login?error=link`. `createUser` passes `redirectTo: <origin>/auth/confirm`, which must be listed in Supabase's allowed redirect URLs. `app/auth/set-password/page.tsx` (`components/set-password-form.tsx`) needs a session (otherwise `/login`), calls `updateUser({ password })`, then the `activateCurrentUser` Server Action (`invited` → `active` in MongoDB), then goes to `/`. The "forgot password" link on the login form goes to `app/auth/forgot-password/page.tsx` (`components/forgot-password-form.tsx`), which calls the `requestPasswordReset` Server Action: it sends the reset e-mail from the server with a plain (non-PKCE) Supabase client so the link carries its tokens in the URL fragment like an invitation, passes no `redirectTo` (the link goes to the Site URL configured in Supabase, which has to be `/auth/confirm`), and answers the same whether or not the address has an account. Sign-up is not implemented.

Application data is MongoDB through the official `mongodb` driver (no ODM), validated with Zod. `lib/mongodb.ts` holds the shared client (`getDb`, `getCollection`; database name comes from `MONGODB_URI`). `models/` has one file per collection from `SPECS.md` section 10, each exporting a Zod schema, the inferred type and a typed collection accessor (`userSchema`, `User`, `usersCollection()`); import from `@/models`. The driver does not validate, so parse with the schema before every write. `ensureIndexes()` in `models/indexes.ts` creates the unique indexes the model relies on; run it with `pnpm db:indexes` (the app never calls it). Amounts are integer centavos; fields that can be absent are stored as `null`, not omitted. Every action that creates, edits or cancels something calls `recordAudit()` (`lib/audit.ts`) with the documents before and after; nothing is deleted, transactions and payments are cancelled with a reason. Queries and Server Actions start with `requireUser()`, `requireAdmin()` or `requireOversight()` from `lib/auth.ts` (they reject a missing or deactivated account) and must await it before starting any query, because that is also what waits for the request. `lib/current-user.ts` (`getCurrentUser()`, cached per request) is the way to get the signed-in user on the server: it returns the Supabase id and e-mail plus `profile`, the MongoDB user document (null if the Supabase user has none). The `(app)` layout uses it for the session check and the sidebar's user block.

### Conventions

- `cn` comes from the **`cn` npm package** (shadcn's compiled clsx + tailwind-merge replacement), not a local implementation. Generated components import it directly (`import { cn } from "cn"`); `lib/utils.ts` just re-exports it. `clsx` and `tailwind-merge` are not dependencies.
- Path alias `@/*` maps to the repo root (there is no `src/`).
- Icons are `lucide-react`, using the `*Icon`-suffixed exports.
- Theme tokens are OKLCH CSS variables in `app/globals.css` (`:root` and `.dark`), exposed to Tailwind via `@theme inline`. Dark mode is class-based (`@custom-variant dark`).
- i18n is `next-intl` without locale routing: Spanish (default) and English, chosen by a `locale` cookie that `i18n/request.ts` reads; `i18n/actions.ts` (`setLocale`) writes it and `components/locale-switcher.tsx` calls that. Messages live in `messages/es.json` and `messages/en.json`, grouped by namespace (`Login`, …); `es.json` is the source of truth for key types (`global.d.ts`). Add every new user-facing string to both files and read it with `useTranslations` / `getTranslations` — no hard-coded copy. A signed-in user changes language from the user menu; `setLocale` also saves it on their document.
- Because the locale comes from a cookie, `app/layout.tsx` wraps the app in `<Suspense>` around `NextIntlClientProvider` (required by `cacheComponents`), so pages are partially prerendered: anything translated renders per request. `<html lang>` is rendered as the default and corrected on the client by `components/html-lang.tsx`.
- Numbers, amounts and dates are formatted the Mexican way (`$85,000.00`, `10,000`): use `getFormat()` (`lib/format-server.ts`) in Server Components and `useFormat()` (`hooks/use-format.ts`) in Client Components instead of next-intl's `getFormatter` / `useFormatter`, and `formatMoney(format, centavos)` (`lib/format.ts`) for pesos. Calendar dates (due dates, payment dates) are stored as midnight UTC and formatted with `timeZone: "UTC"`; timestamps use the condo's time zone (`lib/condo-time.ts`).
- `app/layout.tsx` mounts `ThemeProvider` (next-themes, class-based, system default; pressing `d` outside inputs toggles dark mode) and the sonner `Toaster`, so `toast()` works from any client component.

### Known gaps

- Supporting files (SPECS 6.6: proofs of payment, invoices, restricted files) are not implemented; `models/file.ts` exists but nothing uses it, and there is no S3 configuration.
- The committee cannot see the admin's units list (owners and parking spaces of every unit); it sees owners and balances in `unit-balances/`.
- Inviting a user does not link them to a unit; the admin does that from the units page.
- There is no test runner. `pnpm build` is the best check that every page still compiles and prerenders.
